# Troubleshooting

This document records notable issues encountered while deploying and validating the AWS infrastructure, including symptoms, investigation steps, root causes, and resolutions.

Documenting these failures is intended to show the troubleshooting process used during deployment rather than presenting the environment as if every component worked on the first attempt.

---

## 1. RDS Multi-AZ Subnet Requirement

### Problem

During the initial RDS deployment, AWS returned an error indicating that the selected Multi-AZ DB cluster configuration required three subnets across three different Availability Zones.

### Investigation

The existing network design did not satisfy the Availability Zone requirements of the selected RDS deployment option.

The issue was not related to Security Groups or database credentials; it was an infrastructure design mismatch between the selected RDS deployment model and the available subnet architecture.

### Root Cause

A Multi-AZ DB cluster deployment had been selected even though the project architecture was designed around two Availability Zones.

### Resolution

The RDS deployment was changed to a **Single DB instance**, while retaining private database subnets across two Availability Zones in the DB subnet group.

This provided the network structure required for the project's RDS deployment without unnecessarily deploying a three-AZ Multi-AZ DB cluster.

### Lesson Learned

AWS service deployment options can impose architectural requirements on the underlying network.

Before deploying a managed service, its Availability Zone and subnet requirements should be understood and incorporated into the network design.

## 2. RDS Authentication Failure

### Problem

After successfully provisioning RDS, a connection attempt from the EC2 web server returned:

```text
Access denied for user 'ec2-user'@'10.0.1.234' (using password: YES)
```

### Investigation

Because MySQL returned an authentication error rather than a connection timeout, the network path to the database was already functioning.

This indicated that:

* DNS resolution was working.
* EC2 could reach the RDS endpoint.
* TCP port 3306 was reachable.
* The RDS Security Group was permitting the connection.

The investigation therefore focused on authentication rather than networking.

### Root Cause

`ec2-user` is the Linux operating-system account used to administer the EC2 instance.

It is not a MySQL database account.

The EC2 Linux identity had mistakenly been used as the database username.

### Resolution

The connection was retried using the RDS master database username:

```bash
mysql -h <RDS-ENDPOINT> -P 3306 -u <DB-USERNAME> -p
```

Authentication succeeded.

### Validation

After connecting successfully:

* A database was created.
* A table was created.
* Test records were inserted.
* The records were queried successfully.

This confirmed both network connectivity and database functionality.

### Lesson Learned

Different infrastructure layers use separate authentication domains.

A useful troubleshooting distinction is:

```text
Connection timeout
        ↓
Investigate networking

Access denied
        ↓
Investigate authentication/authorization
```

Reading the error carefully prevents unnecessary changes to working infrastructure.

## 3. Forgotten RDS Master Password

### Problem

The RDS master password was no longer available when database connectivity testing began.

### Resolution

The existing RDS instance was modified and the master password was reset rather than deleting and recreating the database.

The new credential was allowed to finish applying before another authentication attempt was made.

### Lesson Learned

Loss or rotation of a database credential does not normally require rebuilding the database infrastructure.

Credentials should be managed separately from the lifecycle of the underlying database.

A production implementation would also benefit from a dedicated secret-management solution rather than manually managing application database credentials.

## 4. CloudWatch Agent — Missing collectd Dependency

### Problem

The initial CloudWatch Agent configuration failed validation with an error similar to:

```text
Error loading config file:
error parsing socket_listener,
open /usr/share/collectd/types.db:
no such file or directory
```

### Investigation

The error referenced:

```text
/usr/share/collectd/types.db
```

This indicated that the generated CloudWatch Agent configuration contained a `collectd`/socket listener configuration.

The project only required guest operating-system metrics such as memory and disk utilization, so collectd was not necessary.

### Root Cause

The configuration generated by the CloudWatch Agent wizard included functionality that depended on collectd, but the required collectd dependency was not present on the EC2 instance.

### Resolution

Rather than adding an unnecessary dependency, a minimal CloudWatch Agent JSON configuration was created specifically for the metrics required by the project.

The configuration collected:

* Memory utilization
* Disk utilization

This reduced configuration complexity and removed the collectd dependency.

### Lesson Learned

Generated configurations should still be reviewed.

Configuration wizards can enable features or dependencies that are unnecessary for a particular environment.

A smaller configuration containing only required functionality is easier to understand, secure, and troubleshoot.

## 5. CloudWatch Agent — Invalid JSON

### Problem

After replacing the generated CloudWatch configuration, the agent returned:

```text
Cannot translate JSON, ERROR is exit status 1
```

The JSON validator later reported:

```text
Expecting ':' delimiter: line 12 column 10
```

### Investigation

The error explicitly identified JSON parsing as the failure point.

Instead of modifying IAM permissions, reinstalling the agent, or changing network settings, the configuration file itself was validated.

The following command was used:

```bash
python3 -m json.tool /opt/aws/amazon-cloudwatch-agent/etc/cloudwatch-agent.json
```

### Root Cause

The CloudWatch Agent JSON configuration contained a syntax error.

### Resolution

The configuration file was corrected and validated again with Python's JSON parser.

Once validation succeeded, the CloudWatch Agent configuration was loaded and the service was started.

Agent status was then checked with:

```bash
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
-m ec2 \
-a status
```

The agent reported:

```text
status: running
```

### Lesson Learned

Troubleshooting should follow the evidence provided by the error.

Because the failure explicitly referenced JSON translation, configuration syntax was investigated before unrelated components such as IAM, networking, or package installation.

Independent validation tools can also isolate whether a problem belongs to the application or its configuration.

# Troubleshooting Approach

Several general troubleshooting principles emerged during the project.

### 1. Read the Exact Error

Error messages often indicate which infrastructure layer is failing.

For example:

```text
Timeout → Network path

Access denied → Authentication

JSON parsing error → Configuration
```

### 2. Verify Known-Good Components

Before changing infrastructure, confirm which components are already functioning.

This reduces the possibility of breaking working resources while troubleshooting another layer.

### 3. Change One Variable at a Time

Changes were made incrementally so their effects could be observed.

Making several changes simultaneously makes determining the actual root cause more difficult.

### 4. Validate Before Assuming

The project validated infrastructure by testing it directly:

* EC2 web service response
* EC2-to-RDS connectivity
* MySQL authentication
* Database reads and writes
* CloudWatch Agent service status

A resource showing `Available` or `Running` in the AWS console does not necessarily prove that the complete application path works.
